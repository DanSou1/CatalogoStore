# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ExperienceLove — a static, vanilla HTML/CSS/JS product catalog site ("Venta de productos con conexión a whatsapp"). No build step, no package manager, no framework for the site itself (one small exception: an optional Cloudflare Worker, see Checkout below). All product data lives in a single JSON file. Checkout collects shipping details and (once configured) takes real payment through Wompi, but a plain-text WhatsApp message to the merchant remains the fallback/guaranteed notification path regardless of payment status.

## Running / developing

There is no build or test tooling. Open `index.html` directly in a browser, or serve the folder with any static file server (e.g. `npx serve .`) — a real HTTP server is needed for `fetch("./js/productos.json")` and the service worker registration to work correctly (they will fail under `file://` in some browsers).

There are no linters, formatters, or automated tests configured in this repo.

## Architecture

Two pages share the same data/cart model via `localStorage`:

- **`index.html`** — product listing page. Loads `js/main.js`, which fetches `js/productos.json` on page load, renders product cards into `#contenedor-productos`, wires category filter buttons, and renders the rotating `#hero-destacado` carousel. Also loads `js/drawer.js` (slide-over cart panel), `js/promo.js` (countdown bar), `js/testimonios.js` + `js/faq.js` (marketing sections), and `js/temporada.js`.
- **`carrito.html`** — cart page, the only real checkout surface. Loads `js/carrito.js`, which reads the cart out of `localStorage` and renders it independently (it does not re-fetch `productos.json`), plus `js/wompi-config.js` and `js/checkout.js` (shipping form + Wompi payment — see Checkout below).
- Both pages load `js/carrito-storage.js` (shared cart data layer — see below), `js/menu.js` for the slide-out mobile nav (`aside`), and `js/temporada.js` as the very first `<head>` script (so the seasonal theme class lands before CSS paints).
- `index.html` also loads Tailwind CSS via `<script src="https://cdn.tailwindcss.com">` + `js/tailwind-config.js` (runtime JIT, no build step — fine on GitHub Pages since it's fetched client-side like any other CDN tag). Tailwind is used only for the newer marketing sections (hero, countdown, testimonials, FAQ, footer, cart drawer); the product grid and `carrito.html` still use plain `css/main.css` classes. Tailwind's theme colors are mapped to this project's own CSS custom properties (`colors: { plum: "var(--clr-plum)", ... }` in `tailwind-config.js`), so **changing a brand color in `css/main.css` reskins every Tailwind-authored section automatically** — this is also what makes the seasonal theme override work (see below).

**Product catalog (`js/productos.json`)**: flat array of products, each with `id`, `titulo`, `imagen` (relative path into `img/<categoria>/`), `categoria: { nombre, id }`, and `precio`. Product `id`s are prefixed by category, e.g. `lenceria-01`. Optional additive fields: `precioAnterior` (strikethrough + discount badge when greater than `precio`), `stock` (shows a low-stock/"Agotado" label when ≤5, disables Agregar at 0), `destacado` (unused by the current carousel but left available). None of these are fabricated for products that don't have real data — they're simply absent until Daniel sets them.

**Category wiring is implicit and string-matched, not config-driven**: the sidebar buttons in `index.html` (`#cosmeticos`, `#lenceria`, `#Juegos`, `#Juguetes`, `#Bondage`, `#Lubricantes`, `#Sachet`, `#Promociones`) have `id` attributes that `main.js` matches directly against each product's `categoria.id` field via `producto.categoria.id === e.currentTarget.id`. **The casing must match exactly** — most category ids are capitalized (`Juegos`, `Bondage`, `Lubricantes`, `Sachet`, `Promociones`) but two are lowercase (`cosmeticos`, `lenceria`). When adding a new product or category, the `categoria.id` in `productos.json` must exactly match the corresponding button `id` in `index.html`, and product images go under `img/<categoria-folder>/`.

**Promotions carousel (`#hero-destacado` in `index.html`, rendered by `renderCarruselPromociones` in `main.js`)**: auto-rotates (every 4.5s, pauses on hover) through every product whose `categoria.id` is `"Promociones"`. Adding or removing a product from that category is the only thing needed to add/remove it from the carousel — there's no separate carousel config. If the category is empty the whole hero section hides itself (`.disabled`).

**Seasonal theme (`js/temporada.js`)**: a single `TEMPORADA_FORZADA` constant controls the active design — `"auto"` (default, activates Halloween automatically in October via `new Date().getMonth() === 9`), `"halloween"` (force on), or `"normal"` (force off). When Halloween is active, `temporada.js` adds a `tema-halloween` class to `<html>` as early as possible (it's the first script in `<head>`, before any CSS, to avoid a flash of the normal theme); `css/main.css` then overrides the brand CSS variables (`--clr-plum`, `--clr-charcoal`, etc.) under `html.tema-halloween`, which reskins the whole site — sidebar, buttons, product cards, hero, cart drawer — because everything is already built on those variables (including the Tailwind color mapping above). `#barra-halloween` is a banner that's `display:none` by default and only shown under that class.

**Per-product seasonal tagging**: append `.halloween` to a product's `id` in `productos.json` (e.g. `"lenceria-11.halloween"`) to mark it as Halloween merchandise. `esProductoDeTemporada()` / `ordenarPorTemporada()` in `temporada.js` detect this suffix and, only while the Halloween theme is active, sort those products first in both `cargarProductos()` and the promotions carousel, and add a 🎃 badge to their card. No suffix, no effect — this is purely additive and only changes behavior when the matching theme is active. To add a future season (e.g. Christmas), follow the same pattern: a new `html.tema-<nombre>` CSS block plus extending `temporadaActiva()`'s return values — not built yet, by design, until there's a second season to support.

**Cart state (`js/carrito-storage.js` + `js/main.js` + `js/carrito.js` + `js/drawer.js`)**: cart is a plain array of product objects (each with an added `cantidad` field) persisted to `localStorage` under the key `productos-en-carrito`. `carrito-storage.js` is the single source of truth for reading/writing/mutating that array (`leerCarrito`, `agregarProductoAlCarrito`, `incrementarProducto`, `decrementarProducto`, `quitarProducto`, `vaciarArregloCarrito`, `calcularCantidadTotal`, `calcularTotalPrecio`) — `main.js`, `carrito.js`, and `drawer.js` all call into it rather than touching `localStorage` directly. Any mutation dispatches a `carrito:actualizado` `CustomEvent` on `document`, which `drawer.js` listens for to re-render and open itself. The `.numerito` cart-count badges (floating button, mobile header) are updated by `main.js`'s `actualizarNumerito()`, which re-reads from storage every time rather than trusting local state.

**Checkout (`js/checkout.js`, `carrito.html` only)**: clicking "Comprar ahora" no longer messages WhatsApp directly — it shows a shipping form (`#carrito-datos-envio`: nombre, contacto, ciudad `<select>` of "Bogotá D.C." / "Otra ciudad", dirección, and a documento-de-identificación field that's only required when the city isn't Bogotá). Shipping cost is `FLETE_BOGOTA` ($10.000) or `FLETE_OTRA_CIUDAD` ($15.000) in `checkout.js`, added to `calcularTotalPrecio(...)` for the order total.

Payment is Wompi's modal Widget (`https://checkout.wompi.co/widget.js`, loaded in `carrito.html`), driven by `new WidgetCheckout({...})` + `checkout.open(callback)` in `iniciarPago()`. Wompi **requires** an integrity signature (`SHA256(reference + amountInCents + currency + secret)`) that must never be computed client-side (it would expose the secret) — `obtenerFirma()` fetches it from a small external Cloudflare Worker (`server/wompi-signature.js`, deployed separately, see `server/README.md`) rather than the static site itself. `js/wompi-config.js` holds the two editable values this needs (`WOMPI_PUBLIC_KEY`, `WOMPI_SIGNATURE_ENDPOINT`) — same "one constant to edit" pattern as `temporada.js`/`promo.js`. **Until both are filled in** (they ship as `"TU_..."` placeholders), `wompiEstaConfigurado()` returns false and `iniciarPago()` skips Wompi entirely, going straight to the WhatsApp fallback marked "pago por coordinar" — the site is never broken by missing payment config, it just degrades to the old behavior.

Either way — real payment or the fallback — `finalizarPedido()` is what actually notifies Daniel: it calls `enviarCorreoNotificacion()`, which fires a `fetch()` to Web3Forms (`https://api.web3forms.com/submit`, no backend of its own — same "static site, external service" pattern as Wompi) with the full order (items, subtotal, flete, total, all shipping fields, reference, status), which Web3Forms relays to Daniel's Gmail. This happens **automatically**, with no click or action required from the customer — unlike an earlier version of this flow that opened a `wa.me` link requiring the customer to press "Enviar" inside WhatsApp, this is the actual guaranteed notification path. `js/web3forms-config.js` holds the single editable value this needs (`WEB3FORMS_ACCESS_KEY`, obtained free from web3forms.com with just an email, no account) — same "one constant to edit, ships as a `TU_...` placeholder" pattern as `wompi-config.js`; `correoEstaConfigurado()` guards it the same way `wompiEstaConfigurado()` guards Wompi, and a failed/unconfigured send is swallowed (`.catch`) so it can never break the purchase flow.

Wompi's own automatic email receipt to the merchant (built into Wompi, no setup needed) is a second, independent confirmation that money actually moved; it does not carry the shipping address. A `DECLINED`/`ERROR` widget result shows `#carrito-error-pago` instead and leaves the cart untouched (no email is sent in that case).

The cart drawer on `index.html` deliberately does not duplicate any of this — its CTA just links to `carrito.html`.

**`server/wompi-signature.js`**: a Cloudflare Worker, intentionally *not* part of the static site — it exists solely because Wompi's integrity secret can't safely live in client-side code. It's the one piece of this project that isn't "no build step, no backend." Deploying it (`server/README.md`) and creating the Wompi merchant account itself are both one-time setup steps only Daniel can do (they require his ID/RUT/bank account) — nothing in the codebase can complete them.

**Service worker (`js/sw.js`)**: registered from inline script in `index.html` only (not `carrito.html`). Caches the app shell at install (bump `CACHE_NAME` whenever files are added/removed so old caches get evicted), and caches `img/` responses on first fetch. Note the runtime image-caching check (`requestUrl.pathname.startsWith('./img/')`) compares against an absolute pathname, so it will never actually match — image caching via that branch is effectively dead code; images still get cached via the generic fetch handler fallback.

**Styling**: `css/main.css` (CSS custom properties under `:root`, no preprocessor) plus Tailwind CDN for the sections noted above. Toastify (add-to-cart/remove toasts) and SweetAlert2 (cart-clear confirmation dialog) are pulled in via CDN `<script>`/`<link>` tags, not npm. `.disabled { display: none !important }` is the project's hide convention — the `!important` is load-bearing: without it, several Tailwind utility classes (`flex`, `block`, etc.) share the same specificity and would win by source order, silently un-hiding the element.

## Content notes

- All UI text and product data is in Spanish (es-CO); this is a Colombian-market store.
- Prices are stored as plain integers (COP) in `productos.json` and in the cart — all arithmetic (`calcularTotalPrecio`, discount %, flete) operates on those raw numbers. Display-only formatting (`formatearPrecio()` in `carrito-storage.js`, using `toLocaleString("es-CO")` for the thousands-separator look, e.g. `$44.900`) is applied only at the point a price is written into the DOM — never before a calculation.
- Marketing content that isn't backed by real data (currently the testimonials in `js/testimonios.json`) is explicitly commented as temporary/placeholder in its source file — check for that kind of comment before assuming any copy on the site reflects real customers or figures.
